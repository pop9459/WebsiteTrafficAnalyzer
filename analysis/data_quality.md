Generated by `analysis/data_quality.R` on 22 October 2026. Aggregates only.

Dataset: `data/processed/requests.rds` (395,121 parsed requests) and `data/processed/errors.rds` (68,333 error-log lines). Client IPs are replaced by a hash (`ip_hash`) during import.

## 1. Coverage

The requests span 09 July 2026 to 21 October 2026 (UTC), a calendar range of 105 days. 3 of these days have zero requests. 4 day(s) fall below 10% of the median: 09 Jul (25 requests), 04 Oct (0 requests), 05 Oct (0 requests), 06 Oct (0 requests).

Requests per day: median 3,190, interquartile range 1,936 to 4,221, maximum 27,618 (on 14 Oct 2026). A further 14 day(s) lie between 10% and 50% of the median.

The first and last day of the range are usually partial (container created or log fetched during the day), so they can appear as low days without being outages.

## 2. Malformed and unparsable lines

Requests whose request line was not valid HTTP (`probe_family == "malformed"`) are kept: 3,481 requests, 0.88% of all parsed requests. They carry no method or path.

`bytes_in`, `bytes_out` and `duration_us` are structurally missing. They come from the `%I %O %D` directives of the extended log format, which the server writes only since the log persistence change of 7 October 2026 (KAP-49). 96,825 rows have them (from 07 October 2026 on); all older rows lack them by design, which is not a data error. `method` and `path` are missing exactly for the malformed request lines (section 2); `protocol` is missing for those plus a handful of other rows with an incomplete request line. `referer` and `user_agent` are `NA` where the client sent `-` (the parser converts the Apache placeholder to `NA`), so a missing referer (98%) mostly means direct or script traffic, and a missing user agent (11%) means the client sent none. `status` and `bytes` are always present (responses without a body are logged with 0 bytes, 7,449 rows here).

## 4. Duplicates and clock

Exact duplicates (same `ip_hash`, `time`, `request`, `status` and `bytes`): 4,336 surplus rows (1.097% of requests), in 1,836 distinct duplicated keys covering 6,172 rows in total. Apache logs time at one-second resolution, so a duplicate can be a genuine repeated request within the same second (for example a client fetching the same resource twice) rather than a logging error. The rows are kept in the data.

Timezone: `time` carries the tzone attribute `UTC`, `received` carries `UTC`, so all timestamps are UTC. Missing timestamps: 0. Rows are not stored in timestamp order (Apache writes the time when a request starts, so lines of slow requests can appear after later ones).

`received` is the time Docker received the line; `time` is the time Apache logged for the request. Only rows from the Docker export have a `received` time; the server log files written since 7 October do not. The difference `received - time` (seconds) over 298,296 rows: minimum 0.0, median 0.5, 99th percentile 1.0, maximum 3267.0. 0 rows are negative and 11 rows differ by more than 60 seconds.

## 5. Known blind spots

- **Incoming bytes only recently.** `bytes_in` exists only from 07 October 2026 (96,825 rows), so incoming volume before that date, including the 09/2025 spike, cannot be analysed from these logs (this limits KAP-54).
- **Export gap 3 to 7 October 2026.** The manual Docker export ends on 3 October and the persisted server logs start on 7 October (KAP-49), so the days in between are missing here. Those requests exist only in the local-only backup of 7 October (KAP-104).
- **Cloudflare.** 61.1% of requests (241,329 of 395,121) carry a Cloudflare edge address instead of the visitor's (`via_cloudflare == TRUE`; 0 rows undetermined). Per-client statistics, such as requests per IP, are only valid for the remaining direct-to-origin traffic (13,804 distinct hashed addresses overall, mixing both kinds).
- **Start of the data.** Nothing exists before the web container was created on 9 July 2026. The first request in the dataset is on 09 July 2026.
- **Historical logs.** Logs from June 2025 to May 2026 exist only in a local-only backup and are not part of this dataset (KAP-104).
- **Dropped lines.** The count of unparsable log lines is not preserved (section 2).
- **Server-side only.** The logs show requests, not people: there is no session or user identifier, and user agents can be forged.

## 6. Error log

`errors.rds` holds 68,333 lines (Apache error log, stderr) from 09 Jul 2026 to 21 Oct 2026. Lines per day over the 105 calendar days in that range: median 503, interquartile range 209 to 806, maximum 7,562 (on 14 Oct 2026). 6 line(s) carry no timestamp and are left out of the per-day figures. Only the volume is described here; the content of the error log is analysed separately (KAP-71).

## Implications for the analysis

- Daily trends are reliable over the covered range; treat the 4 gap day(s) and the partial first and last day as missing data, not as zero traffic.
- Use `bytes` (outgoing body bytes) for volume over the whole range. `bytes_in`, `bytes_out` and `duration_us` are usable only from 07 October 2026; compare them only within that period.
- Per-client statistics (requests per IP, session-like features) hold only for direct traffic; 61% of requests come via Cloudflare and need a separate treatment until `CF-Connecting-IP` is logged.
- Keep malformed requests as their own probe family instead of dropping them; they have no method, path or protocol.
- Exact duplicates are plausible same-second repeats, so they are not removed.
- Conclusions cover 9 July 2026 onwards only; earlier history needs the local backup (KAP-104).
